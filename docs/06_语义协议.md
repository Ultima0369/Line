# 06 · 上下文打包协议

> 本地侧把多源信息组织成云端能消费的紧凑格式。

---

## 这个协议实际做什么

每次上行（本地 → 云端），边缘处理器把这几样东西打包成一个结构：

```
你的话 + 传感器数据 + 注意力状态 + 上下文摘要
  → 一个带紧凑字段的 JSON（upstream 数据包）
```

云端桥接器据此拼出带环境上下文的 system prompt。

> **诚实说明**：这个模块曾叫"语义压缩协议"，旧文档声称能把传输量压缩 85% 并"天然加密"。
> 实际上传感器数据确实被编码成紧凑串（`tmp:26.5|hum:58.2`，省 token 是真的），
> 但不存在多级压缩、也不存在任何加密。那段叙事已删除。这里只保留真实的能力。

---

## 上行打包（本地 → 云端）

### 传感器数据编码

原始数据：

```json
{
  "temperature": [{"value": 26.5, "unit": "°C", "confidence": 0.95}],
  "humidity": [{"value": 58.2, "unit": "%", "confidence": 0.92}],
  "pressure": [{"value": 1013.0, "unit": "hPa", "confidence": 0.94}]
}
```

编码后（取每类首读数的值，用类型缩写）：

```
tmp:26.5|hum:58.2|prs:1013
```

类型缩写映射见 `line/edge/compressor.py` 的 `TYPE_SHORTHAND`。

### 注意力状态编码

```python
# 原始
{"status": "active", "attention_level": 0.6, ...}

# 编码后
"l:0.6|s:active"
```

### 完整上行数据包

```json
{
  "version": "0.1.0",
  "timestamp": "2026-07-24T09:30:00",
  "type": "upstream",
  "user": "今天天气怎么样？",
  "sensor": "tmp:26.5|hum:58.2|prs:1013",
  "attention": "l:0.6|s:active",
  "context": "t:12|s:[摘要] 用户询问了温度..."
}
```

这个包由 `SemanticProtocol.build_upstream` 产出，`CloudBridge.ask` 消费。

---

## 下行解析（云端 → 本地）

云端返回：

```json
{
  "content": "根据传感器数据，当前温度26.5°C，湿度58.2%...",
  "reasoning": "用户想知道室外天气...",
  "usage": {"prompt_tokens": 120, "completion_tokens": 80}
}
```

本地侧 `SemanticProtocol.parse_downstream` 提取：
- **响应文本**：直接显示给用户
- **推理过程**：可折叠展示
- **建议操作**：从回复中匹配 "建议你/你可以/推荐你/试试" 开头的句子

---

## 这个设计的好处（真实的）

1. **省 token**：传感器状态以紧凑串进 system prompt，而非完整 JSON
2. **结构化上下文**：云端每次都拿到统一格式的环境+注意力+对话状态
3. **可扩展**：想传新类型数据，在 `TYPE_SHORTHAND` 加一个缩写即可
4. **版本控制**：协议有版本号

> 注意：这里**没有加密**。如果你的传感器数据或对话需要保密，应在传输层（HTTPS，已默认）和网络层解决，不要依赖这个打包格式。
